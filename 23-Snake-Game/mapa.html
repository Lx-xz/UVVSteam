Classic Snakes Game Tutorial — MOO ICT · C# / .NET / Windows Forms

O que é

Jogo da cobrinha clássico feito como tutorial, usando Windows Forms. A tela é um PictureBox (picCanvas) onde tudo é desenhado manualmente no evento Paint. Um Timer dispara o game loop e a cobra é uma List<Circle> de células numa grade.

Stack

  • Linguagem: C#
  • Framework de UI: Windows Forms (System.Windows.Forms)
  • Alvos: o .csproj aponta para net10.0-windows (há binários de net8.0-windows também)
  • Desenho: GDI+ (System.Drawing) — Graphics.FillEllipse
  • Sem dependências externas (nenhum pacote NuGet de jogo)

Como rodar

# com o SDK do .NET instalado, a partir da pasta do projeto:
cd "Classic Snakes Game Tutorial - MOO ICT"

Circle.cs modelo

Representa uma célula da grade (não pixels): só X e Y inteiros. Cada segmento da cobra e a comida são um Circle. O nome engana — não tem nada de círculo, é só um par de coordenadas. 

class Circle
{
    public int X { get; set; }
    public int Y { get; set; }
    public Circle() { X = 0; Y = 0; }
}

Settings.cs config estado global

Membros estáticos: Width/Height = 16 (tamanho da célula em pixels) e directions (string: "left"/"right"/"up"/"down"). O construtor só existe para preencher esses valores — por isso o new Settings() "solto" dentro de Form1(). 

class Settings
{
    public static int Width { get; set; }
    public static int Height { get; set; }
    public static string directions;

    public Settings()
    {
        Width = 16;
        Height = 16;
        directions = "left";
    }
}

Form1.cs lógica

Campos:

  • List<Circle> Snake — índice 0 é a cabeça, resto é o corpo
  • Circle food — posição da comida
  • int maxWidth / maxHeight — limite da grade em células
  • int score / highScore
  • bool goLeft, goRight, goUp, goDown — teclas pressionadas

Métodos:

KeyIsDown / KeyIsUpligam/desligam as flags go*. No KeyDown já bloqueiam a inversão de 180° comparando com Settings.directions.

O game loop (GameTimerEvent)

Roda a cada 10 ms. A cada tick:

graph TD
    A[Timer Tick a cada 10 ms] --> B[Ler teclas e definir a direcao]
    B --> C[Percorrer a cobra de tras para frente]
    C --> D{E a cabeca}
    D -->|sim| E[Mover a cabeca uma celula na direcao atual]
    E --> F[Se passou da borda reaparece do lado oposto]
    F --> G{A cabeca esta sobre a comida}
    G -->|sim| H[EatFood cresce um segmento e sorteia nova comida]
    G -->|nao| I{A cabeca esta sobre o proprio corpo}
    H --> I
    I -->|sim| J[GameOver para o timer e atualiza o recorde]
    I -->|nao| K[Segue para o proximo segmento]
    D -->|nao| L[O segmento copia a posicao do segmento da frente]
    L --> K
    K --> M[picCanvas Invalidate]
    M --> N[O evento Paint redesenha tudo]

A cabeça (índice 0) move sozinha; cada outro segmento apenas copia a posição anterior do segmento da frente. Ao final, Invalidate() dispara o Paint.

Por que percorrer de trás para frente?

Assim cada segmento copia a posição antiga do segmento da frente antes que ela seja sobrescrita — é o efeito "vagões de trem". A cabeça (índice 0) é a única que realmente decide para onde ir.

Trecho central

for (int i = Snake.Count - 1; i >= 0; i--)
{
    if (i == 0)
    {
        switch (Settings.directions)
        {
            case "left":  Snake[i].X--; break;
            case "right": Snake[i].X++; break;
            case "up":    Snake[i].Y--; break;
            case "down":  Snake[i].Y++; break;
        }

        // wrap-around nas bordas
        if (Snake[i].X < 0)         Snake[i].X = maxWidth;
        if (Snake[i].X > maxWidth)  Snake[i].X = 0;
        if (Snake[i].Y < 0)         Snake[i].Y = maxHeight;
        if (Snake[i].Y > maxHeight) Snake[i].Y = 0;

        if (Snake[i].X == food.X && Snake[i].Y == food.Y) EatFood();

        for (int j = 1; j < Snake.Count; j++)
            if (Snake[i].X == Snake[j].X && Snake[i].Y == Snake[j].Y)
                GameOver();
    }
    else
    {
        Snake[i].X = Snake[i - 1].X;
        Snake[i].Y = Snake[i - 1].Y;
    }
}
picCanvas.Invalidate();

Observações de design

  • Toda a lógica vive dentro da Form1 — UI e regras de jogo acopladas.
  • Settings é um singleton implícito via static: qualquer parte do código lê e escreve Settings.directions.
  • Não há camada de "modelo de jogo" testável isoladamente.
  • O render é imediato: o estado muda no Tick, o Paint só lê e desenha.

Onde melhorar

🐛 Bugs e corretude

  • Comida pode nascer em cima da cobra — EatFood / RestartGame sorteiam sem verificar posições ocupadas.
  • Comida nunca aparece nas bordas — rand.Next(2, maxWidth) exclui colunas 0, 1 e a última. Deveria ser rand.Next(0, maxWidth + 1).
  • Inversão de 180° ainda passa se duas teclas forem lidas no mesmo tick. A direção deveria ser travada no início do tick, comparando com a direção realmente aplicada no tick anterior.
  • maxWidth/maxHeight calculados só no start — se a janela for redimensionada, a grade e o wrap ficam errados. Recalcular em Resize.
  • GameOver não para o loop imediatamente — o for continua após chamar GameOver(); falta um return/break.
  • Sem condição de vitória quando a grade enche.
  • TakeSnapShot: fonte "Ariel" (erro de digitação de Arial); Bitmap, Graphics e o Label não recebem Dispose() (vazamento de GDI); se o usuário cancela o diálogo, o Label de legenda fica grudado no canvas.
  • highScore só existe em memória — some ao fechar. Persistir em Properties.Settings ou arquivo.

⚡ Performance e responsividade

  • Timer.Interval = 10 (100 Hz) — excessivo e deixa a cobra dependente da CPU. Usar ~120 ms e separar "velocidade do jogo" de "taxa de quadros".
  • PictureBox sem double buffering pode piscar. Usar um Panel/controle custom com DoubleBuffered = true ou SetStyle(...).
  • Colisão O(n) por tick — ok nesse tamanho, mas um HashSet<(int,int)> das células ocupadas resolve em O(1) e ainda ajuda a sortear a comida.
  • Invalidate() repinta tudo — poderia invalidar só os retângulos que mudaram (cabeça, cauda antiga, comida).

🧱 Design e legibilidade

  • Separar lógica da UI — extrair uma classe Game/Board sem dependência de WinForms, testável com xUnit.
  • Settings.directions deveria ser enum Direction, não string — elimina o switch por texto e erros de digitação.
  • Settings mistura constante com estado — tamanho da célula é configuração; direção é estado de partida. Separar.
  • Evitar static mutável — dificulta reiniciar e testar. Passar o estado por instância.
  • Circle como record struct — imutável e com igualdade por valor, simplifica a checagem de colisão (Snake[i] == food).
  • Magic numbers (10 corpos iniciais, cabeça em 10,5, Interval, cores) — extrair para constantes nomeadas.
  • Nomes enganosos — txtScore/txtHighScore são Label; Circle é uma coordenada.
  • using não usados (System.Linq, System.Data, etc.).
  • Faltam recursos comuns — pausa, menu, dificuldade, som, "game over" visível na tela.

Exemplo: direção como enum + trava por tick

enum Direction { Left, Right, Up, Down }

Direction _current = Direction.Left;   // aplicada no último tick
Direction _next    = Direction.Left;   // pedida pelo teclado

bool IsOpposite(Direction a, Direction b) =>
    (a == Direction.Left  && b == Direction.Right) ||
    (a == Direction.Right && b == Direction.Left)  ||
    (a == Direction.Up    && b == Direction.Down)  ||
    (a == Direction.Down  && b == Direction.Up);

void OnKey(Direction requested)
{
    if (!IsOpposite(_current, requested)) _next = requested;
}

void Tick()
{
    _current = _next;          // trava aqui, uma vez por tick
    // ... move a cabeça conforme _current
}
